# TogetherFi Stellar LayerZero V2 receipt adapter

This is an isolated, receipt-only Soroban OApp. It is **not**
linked to `campaign_escrow` (or any token, payout, refund, contributor, or
allocation contract). Native Stellar state remains authoritative. Messages are
optional, informational final-state records; LayerZero delivery failure cannot
change settlement.

The receipt adapter is separate from the optional allowlisted OFT sponsor
funding route. That route delivers tokens into a different Stellar
`FundingInbox`; it does not use this receipt adapter. Receipt messages are
financially inert and carry no campaign principal.

## Status

The adapter is implemented and locally tested, but is not deployed or live. No
real cross-chain transaction evidence is currently claimed. The local tests use
injected or deterministic LayerZero observations and do not demonstrate live
delivery. This README is not an audit or a production-readiness claim.

## Payload

The wire payload is exactly 50 bytes, in big-endian order:

```text
"TFZR" | version:u8 | status:u8 | campaign_id:u64 |
operation_version:u32 | state_hash:bytes32
```

Version is currently `1`; accepted final statuses are `1=COMPLETE`,
`2=REFUNDED`, and `3=ANCHORED`. The `TFZR` domain separator and fixed version
prevent cross-protocol interpretation. Unsupported statuses, malformed lengths,
zero operation versions, duplicate campaign/operation pairs, non-zero inbound
value, wrong endpoint/peer, and skipped/replayed inbound nonces are rejected.

The owner must authorize `send_final_state`. It returns the official
LayerZero `MessagingReceipt` (including `guid` and `nonce`), while
`quote_final_state` uses the official `OAppSenderInternal::__quote` path.
`set_peer`, endpoint/delegate, and OApp receiver methods are generated by the
official `#[oapp]` macro. Inbound handling uses the official endpoint client
to clear the payload and stores no value.

## Reproducible source and toolchain

The official `@layerzerolabs/oapp-stellar-contracts` **1.2.55** package and
its source dependencies are copied under `vendor/oapp-stellar-contracts`.
Their upstream MIT `LICENSE` files are retained. This avoids resolving a
moving `node_modules` package at build time. Do not replace the vendor tree
without reviewing upstream provenance and updating this note.

This package intentionally has its own lockfile and toolchain:

```bash
cd contracts/togetherfi-stellar/contracts/layerzero_receipt_adapter
rustup toolchain install 1.90.0
cargo +1.90.0 generate-lockfile
cargo +1.90.0 test
cargo +1.90.0 build --target wasm32-unknown-unknown --release
```

It targets `soroban-sdk = 25.1.1` and Rust `1.90.0`. The existing contracts
alongside it target SDK 21/Rust 1.81 and must be built separately; there is no
shared workspace or lockfile. No deployment is performed by these commands.

## Focused test status

The current runner has `rustc 1.88.0` and no installed `1.90.0` rustup
toolchain. Consequently, the five native tests were checked with the package
`rust-version` temporarily lowered only in the working copy; all five passed.
The committed package remains pinned to Rust 1.90.0 and must be re-run with
`cargo +1.90.0 test` once that toolchain is available. This is a toolchain
availability limitation, not a deployment or contract test failure.
